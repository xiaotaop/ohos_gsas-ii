## 包与来源

1. 以最新 `main` 和完整运行时为基础，只加入下述最小诊断入口；在收据中列出相对 `791dc53d…` 包变化的源码及 HAP 成员。原生 Core、Python 桥接与科学运行时若保持不变，给出逐字节核对；变化则明确列出并重新审计。
2. C 使用其已有签名权限为原 HAD-W32 制作可覆盖安装的指定设备测试 HAP，不要求组长持有签名材料。若平台要求递增 versionCode，应如实记录；不得卸载或清除现有用户数据。
3. 交付 HAP、SHA-256、源码提交、签名验证、运行时/SBOM/许可绑定和安装说明。诊断入口不得默默进入公开分发包；最终包字节若不同，最终包仍需按其新哈希复核。

## 三项可重复触发的诊断入口

| 场景 | 入口与期望 | 必须可取得的证据 |
| --- | --- | --- |
| 初始化失败后重试 | 测试开关仅让首次 Core 初始化返回一次 `CORE_NOT_READY`，随即自动解除；页面显示失败及 Retry，点击后 Core ready，不清空文件库、输入关联、笔记或历史任务。 | 开关触发/解除时间、两次初始化结果、数据基线前后及页面截图；第二次成功后再跑一次五阶段。 |
| Core-only 第二任务 BUSY | 首任务已通过正式 `startRefinement` 活动时，诊断入口以新的合法 jobId 直接调用同一进程的 Core `acquireJob`；预期第二次返回 `BUSY`，不产生第二文件租约、事件或产物，首任务正常终止。不能用文件服务的 `BUSY` 代替。 | 首任务 jobId、活动快照、第二 jobId/错误码、租约/产物差异、首任务终态。 |
| 取消 ACK 与自然完成竞争 | 在任务尾段重复取消，记录调用时间、ACK、native 事件类型/序号、同 jobId 终态快照及页面终态；覆盖取消先到和完成先到。 | 每次 jobId 的完整时间顺序、恰好一个持久化终态、重启后相同终态；成功产物或取消日志可发现。若一次取消发生在完成后，须标成“晚点”，不算竞争。 |

日志应只输出必要的 jobId、事件类型/序号/时间与错误码，避免科研输入内容、私有路径或凭据。B/组长在收到包后验证 HAP 哈希、覆盖安装与数据保留，再按 [B 的复验步骤](B_PR17_DEVICE_RETEST.md)执行。测试失败保留原始记录，不通过改文档或跳过断言来放行。
