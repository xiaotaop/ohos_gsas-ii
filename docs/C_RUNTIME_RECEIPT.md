# C 与 B 的运行时交接

C 已从固定上游自行构建 8 个 OHOS ARM64 扩展，完成 API26 模拟器上实际 HAP 的科学计算及导出/恢复验收，见 [C_NATIVE_ACCEPTANCE.md](C_NATIVE_ACCEPTANCE.md)。本地开发集成可以继续；用户尚未收到 B 原始归档，B 的 HAD-W32 终端记录应继续按其实际字节独立核验。

B 后续提供以下材料，可用于比对、正式候选冻结与关闭第三方范围审查：

1. 实际完整运行时及 8 模块归档、逐文件清单、源码/头文件/链接输入和可重建配方。B 原扩展归档记录 `f03d81c6bc1935cfe3c802e4f6aff2b7b658b875e47963b0a6cfe79d7f3de2c8`；它不是 C 新构建或完整运行时的哈希。
2. 架构、大小、SHA-256、NEEDED/SONAME、组件归属、源码来源与许可证原文；尤其是捆绑 libffi/GDBM/GNU Fortran/两份 BLAS/SDK C++ 和静态链接组件的准确范围。
3. 解释器和消费者统一 ABI/库名的依据，以及最终 strip/签名/布局后的新 runtimeId 与新清单。C 的独立方案将 133 个消费者绑定实际单份 libpython3.12.so，再重签并做应用内测试，未复制第二份解释器。
4. 原始 PoC/Bridge 输出、执行命令、源码提交和设备系统版本；保留 skipped 及失败记录。B 的 Flang20.1.0 记录不能直接给 C 的 LLVM20.1.8 产物背书。
5. 正式签名及目标真机矩阵所需条件由相应账号/设备持有人提供；无需交付私钥、帐号口令到仓库。

到件顺序：归档安全展开/哈希 → 架构、来源、依赖及严格 8 模块门禁 → strip/签名/布局 → 新清单与 HAP → 实际包 SBOM/许可 → 同一应用的科学、导出、三终态和恢复 → 正式签名、目标设备及组长放行。

本记录随 C 集成验收 PR 交付；未向 B 或组长发送消息。
